## Current B03: OCR first, Vision fallback (30 October 2026)

Production uses `recognizeMeterAssisted`, mode `ocr-vision-assisted`. OCR owns localization; the frame audit preserves accepted frames and permits one OCR redetection only after rejection. A complete eligible OCR proposal stays unchanged without a Vision digit request. If OCR has exactly one explicitly positioned unread slot, a targeted request may read that slot; all known OCR digits remain unchanged. No slot position is inferred from omitted characters.

When neither OCR nor the slot stage produces an eligible proposal, an accepted frame with suitable native image quality may request whole-register Vision fallback. The current `repeated-transcription` method uses two stateless requests: context plus upright crop, then crop only. Neither receives OCR text, expected digits, profile counts, history or the other answer. The production transport requests only `integerDigits`, `fractionalDigits`, `uncertainDigits`; exact group strings must match, preserving leading zeros and without question marks or uncertainty. It does not ask the model to infer meter type, unit or fraction conventions, so the adapter keeps unobserved metadata `unknown`. A confirmed meter profile is therefore required for a fallback proposal and must match observed counts and group boundary; without one, retain observations and request owner configuration. For metadata-rich historical evidence, known type/unit/convention conflicts still veto the result; profile never overrides contradictory evidence. OCR, slot and fallback proposals do not compete: an already valid proposal cannot be replaced by fallback. No units tolerance or averaging applies.

Native photometric checks remain required. An otherwise readable strip below the normal OCR resolution threshold may be tried at native long/short edges at least64/16px. Repeated fallback eligibility additionally requires average native upright strip width divided by observed digit count at least12px and strip height at least24px. This is an average strip-density heuristic, not measured per-cell geometry or a guarantee that every digit is legible. Upscaling does not add native detail. Two requests from one model check stability, not independent correctness. All Vision stages share `TROZY_VISION_TIMEOUT_MS` (default90000), and expired stages do not launch.

The result exposes one `proposedReading` or null, optional `fallbackVision` with two raw observations/derived strings/source image quality, `slotVision`, and `assistance:{version:1,status:'ocr'|'vision_completed'|'vision_fallback'|'unavailable',source:'ocr'|'ocr+vision'|'vision'|null,ocrPattern,filledIndices,issues}`. Repeated-transcription cells have `rectangle:null`; never fabricate geometry. Grounded fallback evidence remains validatable for historical fixtures/snapshots, but the production fallback reader uses repeated transcripts. Original frame decisions remain in `frameEngine/frameProposedReading/frameAssessment`; deterministic validation rebuilds strings, quality and proposal from evidence. Legacy `vision/resolution/comparison/comparisonPolicy` are absent. Always `confirmedReading:null`, `candidates:[]`, `requiresConfirmation:true`.

Owner image/fraction consent, current profile/baseline/CAS and room authorization remain required. Unchanged OCR approval records `ocr-and-human`, a one-slot completion `ocr-vision-and-human`, and a valid whole-register fallback `vision-and-human`; changed/stale values require the existing manual reason. Tenant receipts/list/bootstrap/export stay photo/status-only. The owner sees one proposal, with raw OCR grouped by identical text and angle/score in collapsed diagnostics; differing raw observations are not two official readings. **Đọc lại ảnh** reanalyzes a pending image only when the owner requests it. Recognition does not update business readings or invoices. See [current design](METER-OCR-VISION-ASSISTED.md).

## Historical B03: OCR-localized, Vision-frame-verified (29 October 2026)

At this historical stage, the production registry, meter API and background jobs used `recognizeMeterFrameVerified`. It remains the internal OCR/frame stage. Existing PP-OCRv6 det/rec models own localization and initial transcription. A geometry-only detector-row candidate may trigger whole-row recognition using the same installed recognition model; fragmented text is never concatenated into a result. Printed scale-row context excludes a label such as `100` without banning an actual reading of 100 elsewhere.

Vision receives only images and OCR frame geometry, never OCR digits, confidence, profile counts or history. `accepted` cannot contain a correction. Only a first `rejected` result may suggest a search rectangle; OCR must independently redetect within it and Vision checks that new OCR frame once more. Uncertain or unavailable checks do not permit a correction loop. All coordinates remain in EXIF-oriented source pixels.

This historical mode is `recognitionMode:'ocr-frame-verified'`, with `localization.source:'ocr'` and `frameVerification:{version:1,status,correctionApplied,attempts}`. At most two attempts are allowed. It remains the internal frame stage and supports historical snapshots; its original proposal uses eligible OCR/profile/quality evidence and an accepted frame. The current assistance/fallback stage is described above. See [frame-stage design](METER-OCR-FRAME-VERIFIED.md).

## Historical B03: Vision-guided OCR (earlier on 29 October 2026)

At this historical stage, B03 used `recognizeMeterGuided` from `meter-guided-reader.mjs`. `meter-localizer.mjs` first asked Vision to locate a unique cumulative counter without transcribing digits. Validated coordinates referred to EXIF-oriented source pixels; quality was checked on the actual unscaled counter. OCR then read that crop as the primary proposal source. Independent Vision transcription and a separate per-cell task checked digits, unit, decimal boundary, count and cell geometry. Neither Vision reading task received OCR text, the other answer, profile counts or previous readings. This flow now remains for historical snapshots and diagnostics only; the current production flow is described above.

The historical result uses `recognitionMode:'vision-guided-ocr'`, `assessment:'proposed'|'within_tolerance'|'conflict'|'needs_review'|'unreadable'`, and `proposedReading:null|{digits,displayText,integerDigits,fractionalDigits,unit,value,numericValue,unitSource,boundarySource}`. `confirmedReading:null`, `candidates:[]`, `requiresConfirmation:true` always; `suggestedValue` only mirrors an eligible OCR proposal's whole-unit value. Preserve leading zeros and fractions. Profile and previous-reading snapshots originate from server-authorized state, never tenant input. Runtime/model errors are labeled, never fabricated provider success. Owner review is the sole business write.

`localization:{version:1,status:'located'|'ambiguous'|'unavailable',rectangle:null|{left,top,width,height},sourceWidth,sourceHeight,model,issues}` records the counter source region. `comparisonPolicy:{version:1,maxAbsoluteDifference:0|1,allowedPlace:'units'}` records the policy used for that snapshot. `comparison:{version:1,status:'exact'|'within_tolerance'|'conflict'|'unavailable',maxAbsoluteDifference,allowedPlace:'units',absoluteDifference:number|null,mismatches:[{index,place,ocrDigit,visionDigit}],issues}` records observed differences. `vision`, `cellEvidence`, `ocrProposedReading`, `ocrAssessment` and raw OCR observations retain evidence for deterministic revalidation. The validator rebuilds the OCR proposal and comparison rather than trusting status labels.

`exact` requires the full digit sequence, count, decimal boundary and unit to match, with every physical Vision cell clear and located. `within_tolerance` requires exactly one differing units-position cell, all other cells including fractions identical, and absolute difference within the configured physical unit. Defaults are 1 kWh for electricity and 1 m³ for water, independently configured through `TROZY_METER_ELECTRIC_TOLERANCE` and `TROZY_METER_WATER_TOLERANCE`; only strings `0` and `1` are allowed. A zero threshold permits only exact readings. A numeric difference of one across a carry such as `00999` versus `01000` does not satisfy the single-cell condition. Transitioning, occluded, missing or malformed cells are not tolerance cases. This is an inter-reader difference limit, not an accuracy guarantee. Never average, repair or supplement OCR digits with Vision or history.

Only `exact` or `within_tolerance` can expose an eligible OCR `proposedReading`; conflict/unavailable evidence cannot. Tolerated proposals remain visually distinct from exact agreement. Owner approval always requires `imageChecked:true`; observed/profile fractions require `fractionalConfirmed:true`. Accepting a tolerated proposal requires a 10–1000 character reason even if the submitted value equals OCR, and records `verificationSource:'manual'`; exact eligible OCR plus human review records `ocr-and-human`. The direct-reading form does not offer a quick-apply shortcut for tolerated results lacking the review reason. No recognition, photo submission or review creates/edits an invoice.

Owner-only POST `/api/meter/submissions/:id/reanalyze` accepts `{version}` for a pending submission and returns202 processing. It preserves original files and max3 prior snapshots in owner-only analysisHistory, captures current profile, rechecks tenancy/period/baseline and queues the guided pipeline; no automatic business write. Generic B03 and meter analyses share file.room_id binding and authoritative previous/profile checks before and after async work.

Owner-only GET `/api/meter/profiles?roomId=&utility=` returns `{records}`. PUT `/api/meter/profiles` takes `{roomId,utility,kind,unit,integerDigitsCount,fractionalDigitsCount,configurationConfirmed:true,version?}`; initial version absent/0, update requires matching current version. Unit matches utility; counts are 1..9 and 0..4, total at most13. Profiles are scoped to room/owner, immutable via generic CRUD/import, absent from tenant data. Image snapshots retain profile version; stale settings cannot approve an OCR proposal without explicit manual review. Tenant submission payload remains photos only; receipt/bootstrap/list/export never expose AI readings, profiles, verified values or owner notes. These safeguards still apply to the [current design](METER-OCR-VISION-ASSISTED.md).

Project-owned libraries, portable runtimes, models, datasets, caches, logs and generated data stay under the project root: `node_modules/`, `.runtime/{ollama,paddleocr,meter-digits}/`, `.cache/npm/`, `data/`. Use a distinct project-local task temporary directory and remove only that task's temporary files after completion; preserve originals, business data, libraries/models and reviewed reports. ## Historical B03: OCR-first exact consensus

The B03 payload, orchestration and result-selection description in this section is retained for older hybrid snapshots and tests. It is superseded by Current B03 above and [METER-VISION-GUIDED-OCR.md](METER-VISION-GUIDED-OCR.md); do not reinterpret old test counts or live reports as validation of the new pipeline. The role/tenant-photo safeguards described below remain required unless explicitly replaced by the current contract.

Input `{fileId:string,roomId:string,utility:'electric'|'water',period?:string,previous?:number,meterType?:'auto'|'mechanical'|'digital'|'dial',rectangle?:{left,top,width,height}}`. B03 registry uses `recognizeMeterHybrid` in `meter-vision.mjs`; underlying `recognizeMeter` remains independently usable. No client-supplied model/provider/host or image path/URL/bytes. Prior reading is overwritten by authorized server history.

Current result uses engine `tesseract|paddleocr|hybrid|ollama-vision|quality`, `ocrEngine`, `ocrConfidence`, `assessment:agreed|vision_only|ocr_only|conflict|unreadable|needs_review`, and optional `agreementScope:full|digits`. `engine:quality` is restricted to `recognitionSkipped:true`, failed image quality, empty text/observations and no OCR/Vision result; it never claims an OCR engine ran. `vision` retains independently transcribed digit strings, unit, region role, readability, issues and preparation metadata. Leading zeros are significant: exact full-string agreement is required; numeric equality or integer-only matches never suffice. Role/region validation precedes digit agreement.

Paddle results carry `regions` (max12), each `{regionId,role:'counter'|'serial'|'specification'|'inspection_label'|'unknown',text,evidence:string[],selectable:boolean,sourceRectangle:{left,top,width,height},geometry,observationRegionIds:string[]}`. `sourceRectangle` refers to source pixels after EXIF orientation, undoing OCR canvas rotation and adding the user-crop offset. `geometry.rectangle` remains in the OCR canvas coordinate space. Only `counter`/`unknown` regions can be selectable. Nearby unit/printed weights, window/color layout and serial/spec/year context are conservative semantic layout checks; repeated/high-score digits or area alone cannot establish a counter. Overlapping observations across rotations are merged as the same physical region; an explicit serial/specification veto survives that merge rather than being overwritten by a window cue from another orientation.

`regionSelection:{status:'selected'|'ambiguous'|'unresolved',selectedRegionId?,source?:'layout'|'user'}` selects a unique supported counter, or a unique eligible unknown within an explicit user crop. Competing counters remain `ambiguous`; insufficient support remains `unresolved`. Unselected states cannot produce a confirmed reading, candidates or a suggestion. Raw serial/year/spec observations remain available in diagnostic evidence. This adds bounded heuristics around the existing OCR detector, not a newly trained meter-region detection model.

`confirmedReading` is null unless the region is selected when region evidence is present, Vision independently reports `regionRole:'counter'`, credible independent OCR matches all Vision digits, the Vision unit/decimal interpretation is valid, no credible OCR evidence contradicts digits/unit/boundary, production per-cell evidence is clear and complete, and the selected counter passes server image-quality checks. When present it contains `{digits,integerDigits,fractionalDigits,displayText,unit:'m3'|'kWh',value,numericValue,agreementScope:'full'|'digits',unitSource:'both'|'vision',boundarySource:'both'|'vision'}`. `value` is the integer-only form value; `numericValue` retains the complete physical display. Only a confirmed result may produce `candidates` (one entry, `source:'both'`) or `suggestedValue`. Otherwise both remain `[]`/null, including OCR-only, Vision-only, conflict, partial match, missing unit and decreasing readings. Raw `ocrCandidates`, `registers`, `ocrReadings` and `vision` remain diagnostic evidence, not selectable application values. Backend validation separately rejects malformed roles, rectangles, weights, cell observations, quality objects and confirmed results in unresolved states.

`ocrReadings` carries `{regionId,digits,integerDigits,fractionalDigits,displayText,unit,decimalEvidence,boundarySource,unitSource,complete,stable,scaleEvidence?}`. RGB can observe dark/red ink or wheel backgrounds; a split such as `1303|8` can be rendered `1303.8` for comparison while its unit stays unknown. Color grouping alone does not establish the meter-specific decimal convention: `complete` stays false unless an explicit separator or verified printed positional weights establish the boundary and a positive unit label is observed. `boundarySource` is `ocr-separator|image-colors|printed-weights|unresolved`. Printed-weight evidence is `{source:'printed_weights',fractionalDigits:1..4,labels:['1/10',...],verified:true}`; labels must occur in the actual positional sequence beside the same register and match its red-cell count. A claim injected upstream without observed supporting labels is removed. Unit labels come from image evidence, never the selected utility; `m3/h` and `vòng/kWh` are specifications. Unknown boundaries keep the unseparated digit string.

Vision uses two stateless tasks within one timeout budget, at most two calls. Task one receives whole-meter context plus a padded upright crop from selected-region geometry, never OCR text/answers, confidence or history. Task two receives only the last image, observing non-red and red physical counting windows; it does not receive task one's response. These are two tasks of the same model, not independent engine votes. When explicit region selection is ambiguous/unresolved, preparation does not substitute an arbitrary large OCR crop. The transcription independently requires `regionRole:'counter'|'serial'|'specification'|'unknown'`, covers colored ink and backgrounds, forbids zero padding, guesses and synthetic fractions, and separates digital/mechanical fields. Mechanical electric red fractions require matching visible printed positional weights (`fractionalScale`, `scaleLabels`), never red color alone; water red-group interpretation still requires a visible appropriate `m3` unit. A cell task cannot repair a contradictory transcription. Missing/failed cell evidence preserves the literal observation for review, never confirmation. Raw Qwen `bbox_2d` integer coordinates 0..1000 are normalized for the API; non-red observations allow 13 cells, red observations four, at most 17 raw observations before geometric deduplication and at most 13 physical cells afterward. Declared cell counts are never silently rewritten to match OCR or a desired result.

Frontend shows up to six selectable `counter`/`unknown` boxes in source-image coordinates and lists excluded regions separately. Clicking a box/button clears stale results and fills the crop; **Đọc lại vùng này** starts the next API call explicitly. Region selection never applies a number or saves records. Only `confirmedReading` enables the prominent result and Apply controls; other states show neutral side-by-side evidence. A nonzero fraction requires explicit consent to use the integer part, followed by the existing whole-form confirmation and normal save API. Neither recognition nor region choice saves readings or invoices automatically.

`confidence`/`ocrConfidence` are OCR text scores 0–100, never reading accuracy probabilities; empty OCR text =>0. Lower-than-previous observations remain diagnostic, never selectable. Always `requiresConfirmation:true`. Image-only PNG/JPEG/WebP max5MB,12MP,8000pxperedge; at most two color images, each max3MB, before loopback-only Vision submission. Queue one active/two pending. Model errors retain labeled OCR evidence without offering a single-engine application candidate. `TROZY_VISION_MODEL=qwen3-vl:4b-instruct`, `TROZY_VISION_TIMEOUT_MS=90000`; `TROZY_AI_ENABLED=0|false` disables model calls while keeping OCR. `/api/ai/status` exposes selected OCR engine (`paddleocr|tesseract`) and Vision readiness. Remote-backed models are rejected.

Tesseract preprocessing v2 adds optional `registers` (max2) and `preprocessing:{version:2,attempts:number,regions:number,passes:{regionId,variant,text,confidence}[]}` to B03 results. Its attempt budget is max9 including baseline recognition; diagnostic `passes` holds max8 bounded entries. Each register contains `{regionId,digits,confidence,passes,stable,unit:'unknown'|'m3'|'kWh',decimalEvidence:'unknown'|'separator'|'color_groups',geometry:{kind:'auto'|'user',angle,rectangle:{left,top,width,height}}}` and optional `{blackDigits,redDigits,blackStable,redStable,blackConfidence,redConfidence,blackPasses,redPasses,scaleEvidence}`. Tesseract coordinates refer to source pixels after EXIF orientation. No image buffers/base64 appear in results/history.

Paddle preprocessing v3 uses full-image orientations 0/90/270 and up to two supported counter windows per orientation (3–9 attempts); `preprocessing:{version:3,attempts,regions:0,passes:[]}` counts recognition calls, while `observations` carries their bounded original text and polygons. Crops are quadrilateral-rectified, supporting tilted rows up to the bounded ±65° geometry checks, then projected back to the corresponding rotated/cropped canvas. `geometry` adds `rotationDegrees` and `coordinateSpace:'exif-oriented-crop-then-clockwise-rotation'`. Stable strings still require repeated compatible full/crop observations for the same physical region. Raw OCR characters, including a spurious symbol, are retained rather than repaired into digits.

`ocr-image.mjs` derives Tesseract candidate rows from connected image components, validates glyph size/alignment/spacing, normalizes glyph heights and observes physical background color groups. It does not receive Vision digits or use prior readings to choose a string; no per-photo hardcoded coordinates/digits. This Tesseract path is geometric row normalization. Tesseract digit-only passes use bounded threshold variants120/110/100. `ocr-evidence.mjs` accepts only digit strings matching the observed glyph count; `stable` requires matching strings from at least two distinct variants, no accepted competing string, and mean text score>=65. A single plausible pass remains evidence, not an accepted independent reading. Color groups establish observed layout, not an independently verified unit or decimal position. Black/red strings without their respective stable flags must not be treated as corroborated.

A stable black group matching only the Vision integer group cannot create `confirmedReading` or an application candidate. Full-register ambiguity or unstable red digits cannot be presented as full agreement. OCR-only recognition may return registers/rawText but no candidate or suggestion when unit/decimal evidence is insufficient. Existing explicit-confirmation, authoritative-previous, ACL, queue and subprocess timeout rules remain in force. Historical Tesseract evidence: [OCR-IMPROVEMENT.md](../test/OCR-IMPROVEMENT.md). Current multiple-number region changes and measured limits: [METER-REGIONS-IMPROVEMENT.md](../test/METER-REGIONS-IMPROVEMENT.md).

### Per-cell observations and rolling wheels

Production Vision additionally requires `cellCount:0..13`, `cellsComplete:boolean` and `cells:Cell[]`. Each cell has `{index:0..12,state:'clear'|'transition'|'occluded'|'unknown',digit:''|oneDigit,alternatives:oneDigit[0..2],rectangle:{left,top,width,height}|null}`. Located rectangles are normalized 0..1 in the last image supplied to Vision, with nonzero dimensions and bounds inside that image. Missing localization is retained as `null` (including an all-zero legacy rectangle) and causes abstention, rather than fabricated bounds or loss of the remaining observations. Negative/outside/nonfinite bounds remain invalid. An unclear or transitioning physical window stays in the list with an empty digit; it must not be removed, padded or selected using meter history. `9→0` and other carry transitions have no hardcoded universal lower-digit rule. Syntax errors reject the model response; incomplete counts, inconsistent strings, uncertain cells, excessive box overlap, reversed order or cells outside the rectified counter row cause abstention.

Normalized production `vision` includes `cellEvidenceVersion:1`, `cellCount`, `cellsComplete`, `cells`, and `cellImageIndex:0|1`. Direct validation of historical fixtures can omit these fields; the actual `readMeterVision` call requires them. There is no production fallback that treats missing cell observations as clear.

The merged result adds `cellEvidence:{version:1,status:'clear'|'needs_review'|'unavailable',displayText,expectedCount:0..13,observedCount:0..13,cellsComplete,coordinateSpace:'vision-input-normalized',imageIndex:0|1,cells,issues:string[0..12],alignmentSource:'sequence-position',sourceImage?:{width,height}}`. Aligned cells retain the visual fields and add `ocrDigit:''|oneDigit`, `agreement:'match'|'mismatch'|'unavailable'` and optional `sourcePolygon:[[x,y],[x,y],[x,y],[x,y]]`. Source polygons are inverse-mapped through crop offsets, OCR rotation and deskew into EXIF-oriented original-image pixels, without interpreting digits. Source dimensions are at most8000 per edge/12MP and polygon coordinates must stay within them. Unknown localization has no source polygon. `displayText` masks unclear positions with `?`. Sequence alignment compares independent stable OCR strings at each position; it is not independent character-level OCR localization or a per-cell accuracy score. Different sequence lengths, unavailable/competing OCR digits, transitioning/obscured cells and count mismatches cannot generate a confirmed reading, even when an overall string appears similar. Exact clear-cell strings must match `confirmedReading.digits`; backend validation repeats the geometry/count/string consistency checks. UI presents a cell-by-cell diagnostic grid and mapped overlays on source images, highlighting uncertain/unmatched cells. Boxes are locations proposed by Vision, not proof that the underlying pixels depict the claimed digit.

These checks expose uncertainty reported by the model and reject inconsistent evidence. A VLM can still incorrectly report a clear digit or a plausible box. Neither model agreement, sharpness nor repeated transforms of one photo guarantees physical correctness; owner image review remains required. An optional specialized AMR recognizer must be evaluated separately with licensed data and held-out real images before it can be used as confirmation evidence. A prototype or synthetic-data score must not be described as a validated production recognizer.

### Capture quality and tenant evidence routes

`src/shared/meter-image-quality.mjs` computes technical pixel checks shared by live browser preview and the server. `inspectMeterImage` decodes authorized PNG/JPEG/WebP bytes in RAM, applies EXIF orientation, checks optional source-pixel bounds, and samples the actual counter crop without upscaling. Results are `{version:1,status:'pass'|'retake',canSubmit:boolean,scope:'frame'|'counter',checks:{resolution,exposure,contrast,sharpness,glare},reasons:string[],metrics:{width,height,meanLuma,contrast,edgeEnergy,clippedDark,clippedLight,glareFraction}}`; check values are booleans. Server inspection also retains source dimensions and an optional crop rectangle. These are technical checks, not a probability that the meter value is correct. A passing whole frame retains `canSubmit:false` as an AI/counter-readiness indicator, but may be accepted as a photo-only submission when technical checks pass. Tenant submission no longer requires a successful model analysis or manual crop of the detected counter. Counter readiness is evaluated by the background job for owner review, not displayed as a meter answer to the tenant.

The browser camera uses `getUserMedia` with no audio and an adjustable guide around the entire number row and nearby unit/weights. HTTPS or localhost and camera permission are required. The shutter needs consecutive technically passing, stable preview frames for at least 750 ms, then checks the actual captured pixels again. The uploaded image is independently inspected on the server. Closing/unmounting, leaving the visible document, disabled scope and disconnected tracks stop the camera; stale capture/analysis results are ignored. Uploading an existing image remains available and follows the same server checks.

New routes are separate from the existing landlord-only `POST /api/extensions/B03`:

- `POST /api/meter/quality` accepts exactly `{fileId,roomId,rectangle?}` and returns `{quality}`. Authentication, visible room, authorized file and persisted file `room_id` are checked before decoding.
- `POST /api/meter/analyses` is landlord-only and accepts exactly `{fileId,roomId,period,utility,meterType?,rectangle?}`. Tenants receive403 before model execution, including attempts to submit model/provider/host/results. Owner analysis remains scoped to owned rooms. Client previous/model/provider/host/results are rejected and the previous reading is replaced with the server baseline. New uploads persist `files.room_id` (migration4); the file must belong to the same room/property. Frame failure returns HTTP200 `{id:null,result:null,quality}` before OCR/Vision; a counter that fails analysis readiness returns `{id:null,result,quality}`; an acceptable analyzed counter returns HTTP201 `{id,result,quality}`. Model uncertainty is never automatic approval.
- `POST /api/meter/submissions` is tenant-only and accepts `{roomId,period,utility,photos:[{fileId,rectangle?}],note?}` with1..3 distinct original-photo contents. The photos must be owned uploads of the authenticated tenant for the current active room/contract period and pass server technical quality checks. Client meter values, result objects, analysis IDs and primary AI-answer selection are not accepted. The server persists the photos and a processing state before invoking OCR/Vision, then returns HTTP202 with a redacted receipt. Receipt fields are explicitly limited to `{id,propertyId,roomId,tenantId,period,utility,status,createdAt,updatedAt,photos:[{fileId,createdAt}],reviewedAt?}`; even note/internal fields are not copied into it. A durable server processor reads each photo after receipt, records owner-only evidence and transitions the set to ready-for-review; scanning cannot change readings or invoices. Processing/pending/approved sets block duplicate same-room/period/utility submissions; rejected evidence permits a new set.
- `GET /api/meter/submissions`, bootstrap and `/api/export` apply the same role-sensitive projection. Landlords receive their managed evidence/results for review. Tenants receive only their own receipt, original photo references and generic status/timestamps; no `result`, raw OCR, Vision fields, cell observations, candidate values, analysis IDs, verified value, verification source or internal owner review note. Historical stored snapshots are redacted through this projection without deleting the underlying evidence. Source photos retain their own file ACL; another tenant under the same owner cannot inherit access. Internal baseline fingerprints are omitted from public views.
- `GET /api/meter/updates` is landlord-only and returns `{revision}` computed from that owner's submission state/version/timestamps. Tenant calls return403. While the owner's tab is visible, a light poll runs about every10seconds; a changed revision refreshes bootstrap, including processing completion and the in-app notice. The notice links to the meter evidence page. This is periodic in-app refresh, not an email, external message, OS push or guaranteed immediate delivery under a disconnected/throttled tab.
- `POST /api/meter/submissions/:id/review` is landlord-only. Reject input is `{decision:'reject',version,note}` with a 10–1000 character reason. Approval accepts `{decision:'approve',version,value,imageChecked:true,note?,fractionalConfirmed?,selectedAnalysisId?,readingUpdatedAt?}`. `value` is a whole nonnegative integer at most999999999; the owner must explicitly inspect the image. A different value or an unclear/unconfirmed AI result requires a 10–1000 character manual reason. An observed fractional group requires `fractionalConfirmed:true`. Optional selection must refer to a photo in that submission. `version` prevents duplicate review; UI also sends the current reading timestamp.

Owner-side stored submissions use `{id,propertyId,roomId,tenantId,submittedBy,submittedByName,period,utility,photos:[{analysisId?,fileId,createdAt,rectangle,quality?,result?}],selectedAnalysisId?,note,status:'processing'|'pending'|'approved'|'rejected',version,...reviewMetadata}`. AI fields are populated only by the server processor; owner review is unavailable while processing. Approval adds `verifiedValue`, `verificationSource:'ai-and-human'|'manual'`, `reviewedBy`, `reviewedAt`, `reviewNote`, `fractionalConfirmed` and `readingId`; these fields are owner-only in submission responses. Queued work resumes at startup; a crashed process's lease must expire (default15minutes), while orderly shutdown releases its own lease and ignores late responses. A database lease keeps only one background set active across processors. Model failure still produces `pending` evidence with an explicit manual-review fallback for the owner. Finishing creates a deduplicated in-app notification for the exact landlord account, in the same transaction as the ready state. Recipient-bound notifications are not visible to tenants even under the same property. These records cannot be created, patched or deleted through generic collection operations. Original photos remain separate; the system does not stitch digits across photos or count image transforms as independent captures.

Tenant UI is photo-only: camera/gallery, generic technical quality feedback, remove/retry photo and explicit send. It must not mount owner result/review components, show OCR/Vision or numerical meter values, present manual-AI consent/answer choice, or expose a meter-reading editor. Only the owner chooses a primary evidence photo and verifies/corrects a meter reading. Tenant data projections also omit unconfirmed reading rows so a partially verified period cannot expose an interim value through the regular reading page, B01 context or exports. Normal confirmed-reading/billing history remains a separate existing business capability.

Approval is an atomic transaction covering the submission, reading and audits. It rechecks the active tenancy, the previous baseline and the target utility's captured baseline. Confirmed current readings, any noncancelled current-period invoice (including drafts), or later confirmed readings block this new approval path. An intervening edit to the same utility requires reanalysis; approving the other utility can proceed when its baseline has stayed unchanged. Each approval changes only its verified utility and attaches that source file. `readings.reviewedUtilities` and `meterSubmissionIds` record provenance; `confirmed:true` is set only once both electric and water have been reviewed. No invoice is created or edited by capture, submission or review. Existing manual landlord workflows remain available separately.
